### 2.1 結論(検証用サーバーを本番サーバーとしてそのまま扱わない理由)
1. loopback 限定・出力ルート固定で、別 PC から使えない(GPU サーバーでは使えない)。
2. 開発用サーバー・認証なし・ログ運用なし。`/health` の内部情報は I-3 で除去済みだが、本番公開時の認証・アクセス制御は別途必要。
3. `work_dir` が「サーバーとクライアントで同じパス」を前提にしている(§7)。
4. `mode: test` として `server.yaml` を書くなど、検証専用の前提が随所にある。

暫定運用は **「検証用サーバーを、隔離した専用設定で、この PC の loopback 上で手動稼働させる」** ことに限る。GPU サーバー向けのサーバーは、§8 の条件を決めてから別途設計する(新規の起動モードまたは別エントリ。現行の安全条件は弱めない)。

## 3. 暫定運用の設計(この PC・隔離)
### 3.1 構成
```
[手動起動] inference_server/server.py (推論用 venv、loopback 固定ポート、稼働し続ける)
     ^   GET /health, POST /predict (プロキシなし)
     |
データ作成側(本番モードの経路: inference_server 節なし → app.main は API を起動せず、事前確認 /health を行う)
     work_dir = 隔離出力ルート配下の合成製番フォルダ(同一 PC・同一パス)
     server.yaml = 隔離出力ルート配下(本番共有ではない)
```
**本番モードの経路(`api_preflight`・`request_detections`)を、ローカルの API に向けて確認できる**のが利点。統合モード(アプリが API を起動・停止する)とは別の経路を検証できる。

### 3.3 運用手順(スクリプトと設定は実装済み。**この PC での実動作確認は §14**)
| 操作 | 方法(案) |

### 3.5 スモーク確認スクリプト `tools/smoke_interim_api.py`(I-5。通信部分はモックでテスト済み。fake・sahi の実 API に対する実行結果は §14)
実行方法(API を `tools\run_interim_api.ps1` で手動起動した後、別の PowerShell で。リポジトリのフォルダから):
```
.venv\Scripts\python.exe tools\smoke_interim_api.py [--config app_interim.yaml] [--timeout 秒] [--keep]
```
終了コード: 0 = すべて OK / 1 = 確認に失敗 / 2 = 安全条件により拒否(通信も書き込みもしていない)。

| # | 確認項目 | 内容 |
|---|---|---|
| 1 | 安全条件 | 設定は `app_interim*.yaml` だけ。統合モード・プロキシ使用は拒否。`data.output` と `api.dir_venv` は、**表記上**の位置が `./output_interim` の内側で、そこに至る既存の各階層に**シンボリックリンク・ジャンクション等の再解析ポイントがない**こと(実体解決後に内側に見えても拒否。UNC・ネットワークドライブ・`..` での脱出も拒否)。`server.yaml` の接続先は **127.0.0.1 / localhost のみ**(`::1` を含むそれ以外は接続前に拒否)。`server.yaml` 自体がリンクの場合も拒否 |
| 2 | 事前確認(`/health`) | 製番処理の事前確認と**同じ関数**(`api_preflight.unavailable_reason`)で OK になること |
| 3 | `/health` の本文 | HTTP 200・`ready: true`・内部情報(`output_root`・`pid`)を含まないこと(§5 の目標契約) |
| 4 | 推論の依頼 | 合成の白い PNG 1 枚の製番フォルダ(`./output_interim/smoke/smoke_<乱数>`)に対し、本番モードと同じクライアント(`pipeline.inference_client.request_detections`、プロキシなし)で依頼できること |
| 5 | 検出結果ファイル | `1_detected.txt` ができ、UTF-8 で読め、各行が契約の形式(`Index$…|Device$…|Score$…|Coordinates$…`)であること。0 件(空ファイル)は正常 |

- **対象データ・接続先の範囲**: 合成データだけ。実図面・ホスト DB・設計サーバー・CAD・本番共有・実タスクには触れない。外部ホストへは接続しない(loopback 以外は拒否)。
- **書き込み・削除の範囲**: 常に `./output_interim/smoke/` 配下だけ(設定の `data.output` には依存しない)。作るのは、この実行が**新規に**作る合成フォルダ(`smoke_<乱数>`。既存の同名は使わず失敗)と、その親で新規に作ったものだけ。フォルダ内に乱数の印(`.smoke_owner`)を置き、**終了時は印を確認できたフォルダだけ**を削除する(想定外のリンクを検出したら何も削除せず `NOTE:` を表示)。新規に作った親は、空のときだけ削除する。`--keep` で残せる。拒否ケース(終了コード 2)では、通信・書き込み・削除をしない(テストで、ファイル一覧とハッシュが不変であることを確認)。
- **出力**: 固定の文言だけ。接続先・パス・認証情報・例外メッセージ・API の依頼ログは表示しない(例外型と件数だけ。`image_mod` の標準出力も捨てる)。
- `--timeout` は**スモーク専用**の待ち時間(既定 120 秒)。`api.request_timeout`(GPU 環境での実測まで未設定)とは無関係で、値の決定には使わない。
- 前提: API の出力ルートと `app_interim.yaml` の `data.output` が同じ(既定の `output_interim`)こと。異なると、サーバーが `work_dir` を拒否して 4 が失敗する。
- 確認できないこと: §3.4 のとおり(性能・別 PC・プロキシ・共有ストレージ・実図面)。

### 3.4 暫定運用で**確認できない**こと

## 5. `/health` の目標契約
| 状態 | HTTP | 本文(`status`) | 備考 |
|---|---|---|---|
| モデル準備完了 | **200** | `ok`・`ready: true` | クライアントが続行してよい唯一の状態 |
| 起動中(モデル読み込み中) | **503** | `loading`・`ready: false` | 再試行してよい |
| 準備失敗 | **500** | `failed`・`ready: false`・短いエラー型名 | 再起動・調査が必要。内部パス・スタックトレースは返さない |

- **リダイレクトなし**(3xx を返さない)。クライアント(事前確認)も追跡しない。
- 認証: **未決定**(§10)。現状は認証なし。ネットワークに出す場合(GPU サーバー)は要検討。
- 本文に内部情報(出力ルートのパス・pid)・例外メッセージを含めない(**実装済み**: 検証用サーバーの本文は `instance_id`・`backend`・`mode`・`status`・`ready` と、失敗時の `error`〔例外の型名だけ〕。§4 I-3)。
- `/predict` も準備中は 503、準備失敗は 500(現行どおり)。
- 検証用サーバーは、**状態コードの対応(200/503/500・リダイレクトなし)は目標と一致**している(変更なし。テストで固定)。`/predict` の失敗応答(500)のメッセージには、従来どおり例外の短いメッセージが含まれる(今回の範囲外)。

## 6. `/health` チェックの整合(運用画面と製番処理の事前確認)
> **実装済み(案 A)**: 運用画面の確認は、事前確認と同じ関数を使うようにした。以下 6.1 は変更前の差の記録。参考行(案 B)は追加していない。

### 6.1 変更前の差(結果が異なり得た)
| 観点 | 運用画面の動作チェック(`ops/checks.py`) | 製番処理の事前確認(`api_preflight.py`) |
|---|---|---|
| プロキシ | **常に使わない** | `/predict` と同じ(`api.use_proxy`、`server.yaml` の `proxy`) |
| リダイレクト | **追跡する**(転送先の 200 で OK になり得る) | **追跡しない**(3xx は失敗) |
| 待ち時間 | 3 秒固定 | 既定 5 秒(`api.health_timeout`) |
| 失敗の分類 | 接続拒否の案内あり | 接続拒否・タイムアウト・HTTP コードを固定文言で |
| 接続先の決定 | `server.yaml` の `host.pc_ip` / `host.port` | 同じ |

⇒ プロキシ必須の環境では、**運用画面は NG・事前確認は OK**(または逆)になり得る。リダイレクトがある場合は、運用画面が OK でも事前確認は失敗になり得る。**運用画面が OK でも製番処理が止まる(またはその逆)状態が起き得る**。

### 6.2 整合の選択肢
| 案 | 内容 | 利点 | 欠点・影響 |
|---|---|---|---|
| **A(推奨)** | 運用画面の `/health` 確認を、事前確認と**同じ関数**(`api_preflight` の確認ロジック)に寄せる。画面の表示は、事前確認と同じ結果・同じ文言になる | 「画面が OK = 製番処理の事前確認も OK」を保証できる。差が構造的になくなる | 画面でプロキシ経由の確認になる(プロキシ設定が誤っていれば NG になる。それが本来の確認)。ops の既存テストの更新が必要 |
| B | 画面に**2 行**表示する: 「製番処理と同じ経路」と「プロキシなし(参考)」。差があれば原因の切り分けに使える | 経路の問題(プロキシ)を切り分けられる | 画面が複雑になる。OK/NG の意味の説明が要る |
| C | 現状維持し、画面に「プロキシなしの確認」と明記するだけ | 変更が小さい | 食い違いが残る。利用者が誤解し得る |

提案: **A を基本**にし、必要なら B の「参考行」を追加する。判定(`OK`/`NG`)は事前確認と同一にし、「参考行」は判定に含めない。暫定運用(`use_proxy: false`)では差は出ないが、GPU サーバー移行で顕在化するため、移行前に A を入れておく。

## 7. `work_dir` の共有(GPU サーバー移行の条件)
- 現在の `/predict` は、**画像そのものを送らず、`work_dir`(パス)だけを渡す**。サーバーがそのパスのファイルを読み、結果ファイルを同じ `work_dir` に書く。
- したがって API を別の GPU サーバーへ移す場合は、**次のどちらか**が必要。

| 方式 | 内容 | 条件・影響 |
|---|---|---|
| **S: 共有ストレージ** | クライアントとサーバーの**両方から同じ製番フォルダが読み書きできる**共有を置く | 同じパスで見える必要がある(クライアントが送るパス文字列を、サーバー側で解釈できること)。サーバーが Windows なら UNC・同一表記で可能。**サーバーが Linux の場合、Windows のパス(`C:\…` / `\\…`)は絶対パスとして解釈されず、拒否される**(現行 `os.path.isabs`)。パスの対応づけ(変換)層が要る。共有の反映遅延・書込権限・排他の設計が要る。現行のサーバーは UNC を既定で拒否する(`allow_unc`)ため、安全条件の再設計が要る |
| **U: 画像を送る** | `/predict` で画像のバイト列を API へ送り、結果(検出テキスト・可視化画像)を応答で返す。クライアントが製番フォルダへ書く | **契約の変更**(リクエスト・応答・クライアント `image_mod.slice_prediction_request`〔リポジトリ外の社内コード〕の変更)。共有ストレージ不要。送信サイズ・タイムアウトの設計が要る。サーバーはファイルシステムに触れなくなり、安全面は単純になる |

- 暫定運用(同一 PC)では **S の特殊形(同じローカルパス)**で足りる。
- どちらにするかは **未決定**(§10)。U は `image_mod`(リポジトリ外)の変更を伴う点が最大の影響。

## 9. コンテナ化の必要性の比較(必須とは決めない)
| 観点 | 仮想環境(venv)で運用 | コンテナ(Docker 等) |
|---|---|---|
| 暫定運用(この PC・Windows) | **十分**。既存の推論用 venv・起動方法をそのまま使える | GPU 利用に WSL2 / NVIDIA コンテナ環境が要る。ローカルパス(`work_dir`)のマウント・パス対応が複雑になる。**得られるものが少ない** |
| `work_dir` のパス | OS ネイティブのパスをそのまま使える | Linux コンテナでは Windows のパスが使えない(§7)。パス変換か、画像を送る方式(U)が前提 |
| 依存関係の再現(torch/CUDA の版) | 版固定の `requirements-real.txt` と記録で運用。環境差が出やすい | 版を含むイメージで再現しやすい(GPU サーバーでの再配置・復旧が簡単) |
| GPU サーバー(Linux の場合) | 手動の venv 構築・CUDA 整合が必要 | NVIDIA ドライバ以外を同梱でき、**再現性・移行のしやすさで有利** |
| GPU サーバー(Windows の場合) | 現状の構成を踏襲しやすい | Windows コンテナでの GPU 利用は制約が多く、**不向き** |
| 運用負荷 | 低い(手動起動・手動停止の方針に合う) | イメージの作成・更新・保管が増える |
| 起動の自動化 | しない方針(決定) | 自動化は可能だが、方針上は使わない |

判断: **暫定運用では不要**。GPU サーバー移行時に、(1) サーバー OS、(2) `work_dir` の方式(S / U)、(3) 再現性の要求、(4) 保守担当の習熟度、を決めてから再評価する。目安は、**Linux の GPU サーバー + 方式 U なら導入の価値が高く、Windows サーバー + 方式 S なら venv で足りる**。

## 15. 暫定 API 操作画面(ローカル専用 UI。`interim_console.py`)
Sahi の暫定 API を、ブラウザーから「起動・状態の更新と表示・合成 PNG 1 枚のスモーク・停止」できる画面。運用画面(`ops_console.py`)とは独立で、製番処理・DB・共有・CAD・タスクスケジューラには触れない。

### 15.1 使い方
```
.venv\Scripts\python.exe interim_console.py serve [--port N]     # 既定は 8771〜8790 の空いている最初のポート(127.0.0.1 のみ)
```
ブラウザーで、表示された `http://127.0.0.1:<ポート>/` を開く。最初の画面に URL と手順が出る。
1. **起動**: Sahi API を起動(モデルの読み込みに 20〜60 秒。状態は 起動中 → 準備中 → 準備完了)。 2. **更新**: 状態の再取得(2 秒ごとに自動更新)。 3. **スモーク実行**: 準備完了後に、合成 PNG 1 枚で 5 手順(安全条件・事前確認・`/health` 本文・`/predict`・検出結果ファイル)を確認し、成否と**検出件数だけ**を表示(0 件は正常)。 4. **停止**: この画面が起動した API だけを停止。画面を閉じても、画面サーバーを止めても、API は止まらない。

状態の表示: 待機中 / 起動中 / 準備中 / 準備完了 / 失敗 / 外部起動中。スモークは 実行中 / 成功 / 失敗。処理中は該当ボタンを無効化し、二重起動・二重実行は 409 で拒否する(スモーク中は起動・停止も不可)。

### 15.2 ローカル設定(Git 管理外)
モデルのフォルダと推論用 venv の python は、`interim_console.local.yaml`(キー `model_dir` / `python`。`*.local.yaml` として Git 管理外)から読む。**値は画面・応答・ログ・追跡対象ファイルに出さない**(画面には「設定済みか」だけ)。使えない設定(相対パス・UNC・ファイルなし・`python*.exe` 以外)では起動を拒否する。

### 15.3 安全条件(実装とテスト)

## 16. 製番の指定実行と、全製番の仮定期実行(暫定 API 操作画面。2026-10-23 までの仮運用)
暫定 API 操作画面(§15)に、次の 2 つを追加した。どちらも**既存の製番処理 `app.main()`(→ `run_product`)をそのまま呼ぶ**(処理ロジックは重複実装しない)。実行管理(二重起動の防止・COM の初期化と終了・履歴・`SystemExit` の扱い)は、既存の `ops/runner.py`・`ops/history.py`・`ops/scheduler.py` を再利用する。

### 16.1 画面の使い方
**製番を 1 件指定して実行**
1. 製番(英数字 4〜20 文字)を入力すると、**実行前に出力先(隔離領域内の相対パス)**が表示される(既に出力がある製番は、処理済みとして「スキップ」される旨も表示)。
2. 推論 API が「準備完了」であること(§15。未起動なら、固定の文言で拒否される)を確認して **実行**。
3. 状態(実行中 / 完了 / 失敗 / スキップ)と、完了後の**生成ファイル(相対名とサイズ)**、下部の**実行履歴(直近 10 件)**を確認する。実行中は実行ボタンが無効になり、二重起動は拒否される(別プロセスの定期実行とも排他)。実行中は、API の停止も拒否される。

**全製番の仮定期実行(専用タスク)**
- 開始時刻と間隔(日。**既定 2 日 = 1 日置き**)を指定して **登録・更新**。**解除**、**状態更新**(登録の有無・有効/無効・間隔・時刻)。
- **タスクは、この PC にログオンしている間だけ動く**(ログオフ中・スリープ中は動かない)。この注意は、画面に常時表示される。
- 実行内容は、全対象製番(ホストの出図済み − 出力済み)を通常処理で 1 回。**API は手動起動**のため、未起動のときは、事前確認で失敗として履歴に残る(製番処理は始まらない)。

### 16.2 既存の本番設定・本番タスクからの分離
| 項目 | 本番・通常運用 | この仮運用(専用) |
|---|---|---|
| 設定ファイル | `app.yaml` / `app.local.yaml` | `app_interim.yaml`(実行のたびに検証。他の名前・`app.local.yaml` は使わない) |
| 出力先 | 設定の `data.output`(共有)。`output_root` の上書きも可 | **`output_interim` の内側だけ**(`output_interim/a_product/output/<製番>`)。`output_root` の上書きは使わない |
| 定期タスク名 | `SekisanNaviData_Ops`(通常の定期タスク。**この画面は一切参照・操作しない**) | `SekisanNaviData_InterimOps`(`SekisanNaviData_Interim` で始まる専用名だけ受け付ける。通常のタスク名は受け付けない) |

### 16.3 安全条件(実装とテスト)
- **隔離の検証は、製番の指定実行・タスクの登録・タスクの実行(`run-scheduled`)のたびに行う**: 専用設定の `data.output` と `api.dir_venv` が `output_interim` の内側であること(表記上の位置で判定)、そこに至る既存の各階層にリンク・ジャンクションがないこと、UNC・ネットワークドライブでないこと、統合モード(アプリが API を起動する設定)でないこと、`use_proxy: false`。満たさなければ、`app.main` を呼ばず、固定の文言で失敗とする。実行直前にリンクが作られた場合も、worker の中で再検証して拒否する(テストで確認)。
- ホスト DB・設計データは、既存の製番処理が**読み取りだけ**で使う(この変更で処理は変えていない)。生成物(製番フォルダ・PDF・印刷スクリプト・ログ)は、すべて隔離先の製番フォルダ配下。共有の出力先には書き込まない。
- **失敗時の後始末は、既存の安全な処理に任せる**(`run_product` の、出力ルート配下に限る製番フォルダの削除。`SystemExit` も同じ後始末)。この機能のコードは、製番フォルダを削除しない(テストで、削除系の呼び出しがないことを確認)。
- 履歴・画面に出す理由は、**例外の種類名だけ**(例外メッセージ=パス・ホスト名・接続先を含み得るものは、履歴ファイルにも画面にも残さない)。固定の文言(処理済み・事前確認の理由など)はそのまま。画面・応答には、絶対パス・設定値・製番以外の識別情報を出さない。
- タスク: 同名で、この画面のものではないタスク(起動入口が `interim_console.py` でないもの)は、**上書きも解除もしない**。通常のタスク名は受け付けない。登録できない設定(時刻・間隔の不正、起動コマンドが `schtasks` の上限 261 文字を超える)は、`schtasks` を呼ばずに拒否する。
- 状態変更の操作は、専用ヘッダ・Host・Origin の検査を通ったものだけ(§15.3)。待受は 127.0.0.1 のみ。
