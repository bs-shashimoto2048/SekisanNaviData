## 3. 待受範囲
- **設定の `bind.host` に書いた IPv4 アドレス 1 つだけ**で待ち受ける。`0.0.0.0`・`::`・IPv6・ホスト名・マルチキャスト・リンクローカルは設定の検証で拒否する(`ConfigError`)。
- ポートは固定(`bind.port`、1024〜65535)。0 や自動採番は不可(旧サーバーは起動のたびにランダムだった)。
- この PC だけで使うなら `127.0.0.1`(外部から到達できない。最も安全)。LAN に出す場合は、その PC のアドレスを 1 つ明示する。
- 既定値は持たない。`mode: production` を含め、書き忘れは起動拒否。
- 起動前に `check` で「そのアドレスがこの PC に割り当てられているか」「ポートが使用中でないか」を確認できる。使用中の判定は、指定アドレスと loopback への接続試行で行う(Windows では、ワイルドカードで待ち受ける旧サーバーがあっても、特定アドレスの bind が成功することがあるため、bind の成否だけに頼らない。`serve` も同じ確認をして終了コード 3 にする)。
- サーバー実体は **Waitress**(本番用 WSGI サーバー。§6.5)。`bind.host`・`bind.port` の 1 つだけで待ち受け、起動後に実際の待受アドレス・ポートが設定と一致することを確認する(一致しなければ使わない)。

## 4. 認証・ネットワーク制御
現在のクライアント(`bs_pkg.image_mod.slice_prediction_request`)は、`work_dir`・`page_nmb`・`extension` のフォームだけを送り、**ヘッダー(認証情報)を付けられない**。`bs_pkg` はリポジトリ外(社内コード)のため、このリポジトリの変更ではクライアントを変えない。そのため、既定の防御は**ネットワーク制御**に置く。

1. **接続元の許可リスト(必須)**: `allowed_clients` に IP / CIDR を 1 つ以上、明示する。それ以外の接続元は、全ルートで **403**。IPv6・解釈できないアドレスは拒否。`0.0.0.0/0` や IPv4 で `/24` より広い範囲は設定の検証で拒否する。`X-Forwarded-For` などのヘッダーは信用しない(ソケットの接続元だけを見る)。
2. **プロキシ経由の注意**: クライアントの `api.use_proxy`(省略時 true)で、`server.yaml` の `proxy` を経由して接続する場合、サーバーから見える接続元は**プロキシの IP**になる。その場合、許可リストにプロキシの IP を入れる必要があり、**そのプロキシを使える全員が接続できる**ことになる。推奨は、この PC のクライアントから、この PC のアドレスへ**プロキシなし**で接続する構成(許可リスト = この PC 自身 1 件。アプリ側の設定 `api.use_proxy: false` が必要。**アプリの設定変更は本実装の範囲外**で、運用担当が行う)。
3. **`/health` の公開範囲**: 許可リストに含まれる接続元だけ。本文は最小限(状態・instance_id・モード・モデルの識別情報)で、パス・アドレス・プロセス ID・ハッシュ全文・例外メッセージを含まない(テストで固定)。
4. **任意の Bearer トークン**: `auth.token_file` を設定すると、`/predict` に `Authorization: Bearer <token>`(24 文字以上、定数時間比較)を要求する。**現行クライアントが送れないため、対応するまで使わない**(設定すると製番処理がすべて 401 になる)。`/health` はトークン不要(許可リストのみ)。
5. **`/predict` の入力検証(§7)**: 許可リストを通過した相手でも、設定した出力ルートの外を読み書きできない。
6. **提供しないルート**: `/shutdown`・`/verify_workdir` は持たない(停止はシグナル: Ctrl+C / SIGTERM / SIGBREAK だけ)。
7. **限界**: TLS なし(HTTP)。認証は任意で、現行クライアントでは使えない。許可リストは IP ベースで、同じ許可 IP 上の別プロセスは区別できない。Windows ファイアウォールなどの OS 側の制御と併用することを推奨する(本実装は設定しない)。

## 5. `server.yaml` の更新動作
クライアントと運用画面(8765)・製番処理の事前確認が読む接続設定(`api.dir_venv` / `api.yaml_file` の共有 `server.yaml`)の更新は、**サーバーの起動と切り離し、明示した操作にする**。

### 5.1 いつ書くか
| 起動の仕方 | 動作 |
|---|---|
| `check` | 書かない。計画(どのキーが変わるか)だけを出す |
| `serve`(既定) | **書かない**。待ち受けと `/health` だけ |
| `serve --publish-config` | **モデルの読み込みが終わってから**、下表に従って書き、**書けたら ready にする**(公開に失敗したら ready にならず、API を停止する) |
| `serve --publish-config --replace-stale` | 既存が応答しない(古い)ときの上書きも許可する |

### 5.2 判定(`--publish-config` のとき)
| 既存の `server.yaml` | 動作 |
|---|---|
| 無い | 新規に作る |
| 読めない(壊れている) | **拒否**(終了コード 5)。手動で確認する |
| あり、接続先が `/health` に**応答する**(自分以外・形式不明を含む) | **常に拒否**(`--replace-stale` でも不可)。稼働中の別 API の接続先を奪わない |
| あり、稼働中かどうか**判定できない**(読み取りタイムアウト・到達不能・名前解決失敗・接続先が IPv4 とポートの数値で読めない) | **常に拒否**(`--replace-stale` でも不可)。手動で確認する |
| あり、接続先が**接続を明示的に拒否した**(TCP の接続拒否) | 「古い設定」。`--replace-stale` が無ければ**拒否**。あれば、退避してから置換 |

「古い」と判定してよいのは、接続拒否だけ(旧サーバーが推論中で応答が遅いだけ、別セグメントで到達できないだけ、の場合に上書きしないため)。
共有の一時的な切断・権限不足でファイルを読めないときも、「無い」とは扱わず(`unreadable`)、拒否する。

公開できない状況は、**待ち受けを始める前に**判定して終了する(終了コード 5)。準備完了後に公開できなかった場合も、API を停止する。

### 5.3 書き込みの手順
0. 同じフォルダの排他ロックファイル `server.yaml.lock`(`O_EXCL`)を取る。既にあれば拒否(別の公開が進行中。異常終了で残った場合は、稼働中の公開が無いことを確認して手動で削除する)。終了時に自分のロックを解除する。
1. 既存ファイルを**1 回だけ読み**、そのバイト列を `publish.backup_dir` へ `server.yaml.bak-<UTC日時>-<instance先頭8桁>` として書き(同名があれば拒否。上書きしない)、内容の一致を確認する。
   新しい内容は、同じバイト列を解釈して作る。
2. **置換の直前に再確認**: 既存の内容が変わっていないこと(ハッシュ)、接続先がまだ使われていないこと(`/health` をもう一度)。変わっていれば拒否(他者の書き込みを黙って上書きしない)。
3. 同じフォルダの一時ファイルへ書き、`os.replace` で置換する(原子的。途中状態を読ませない)。共有上で読み取り中のクライアントと衝突して `PermissionError` になることがあるため、短く再試行する(最大 5 回)。
   失敗しても一時ファイルを残さない。すべての失敗は固定の理由コード(`write_failed` など)にして、終了コード 5 で停止する。
4. 書き込み後に読み直し、`instance_id` が自分のものであることを確認する(不一致は失敗)。

### 5.4 書く内容(更新されるキー)
| キー | 内容 |
|---|---|
| `host.ip` / `host.pc_ip` | 設定の `bind.host` |
| `host.port` | 設定の `bind.port`(固定) |
| `host` の他のキー | 既存のまま(保持) |
| `proxy.host` / `proxy.port` | **既存のファイルの値を引き継ぐ**。既存が無い(または proxy が無い)ときだけ設定の `publish.proxy`(省略可) |
| `directory.output` | 既存のファイルの値を引き継ぐ(クライアントは読まない) |
| 上記以外の既存のキー(未知のキー) | **そのまま保持する**(消さない。リポジトリ外のツールが読むキーが消えないように) |
| `mode` | `production`(追加) |
| `instance_id` | 起動ごとの識別子(追加。`/health` の値と一致) |
| `model.id` / `model.weights_sha256_12` / `model.yaml_sha256_12` / `model.weights_size` | モデルの識別情報(追加。ハッシュは先頭 12 桁だけ) |

変えるのは上記の ip・port・pc_ip・mode・instance_id・model だけ。クライアント(`bs_pkg`)が読むのは `host.pc_ip`・`host.port`・`proxy.*` で、追加キーは読まれない(この点はリポジトリ内のコードで確認した範囲。`bs_pkg` 以外の読み手は未確認)。

### 5.5 影響範囲と戻し方
- 影響を受けるのは、この共有 `server.yaml` を読むすべて(運用画面 8765 の動作チェック、`SekisanNaviData_Ops` の定期実行・手動実行、他の PC の利用)。**公開は、その実行が無いときに行う**(§9)。
- 停止しても `server.yaml` は削除しない(古い設定として残る。クライアントには「接続が拒否されました(API 未起動、または server.yaml の接続先が古い)」と表示される)。次回の起動時に `--replace-stale` で更新する。
- 戻すには、退避したファイルを `server.yaml` へコピーする(この API を停止してから)。

## 6. モデルの識別・照合
### 6.1 設定(`model`)
`id`(識別名)・`dir`・`weights`(ファイル名のみ)・`yaml`・`expected`(`weights_sha256`・`weights_size`・`yaml_sha256`)を**すべて明示**する。期待値は、管理担当が控えた版の記録(`docs/acceptance_handoff.md` §5〜6 の「ファイル名と SHA-256 を控える」手順)から転記する。値はリポジトリに書かない。

### 6.2 照合のタイミング
1. **起動前(待ち受ける前)**: 重みと `model.yaml` を**元のファイルから 1 回だけ読み**、ハッシュを計算しながら、私用の一時フォルダ(ステージング。読み取り専用)へ書き出す。ハッシュとサイズは**コピーしたバイト列**について期待値と照合し、
   **一致しなければ起動しない**(終了コード 4。ステージングは残さない)。重み・`model.yaml` はリンク・フォルダ・欠落を拒否。`model.yaml` の `model.my_model` が設定の `weights` と一致することも、ステージングしたコピーから確認する。
2. **読み込み**: バックエンドは**ステージングした(検証済みの)コピーだけ**から読み込む。検証・コピーの後に元のファイルを差し替えても、検証済みでないものは読み込まれない
   (`.pt` は pickle のため、検証前のファイルを読み込むとコードが実行され得る点への対策)。読み込み後にコピーの変更がないことを確認し、コピーは削除する。読み込みに失敗したら API は停止する(終了コード 6)。
3. **`/health`**: `model: {id, weights_sha256_12, yaml_sha256_12, weights_size}`(ハッシュは先頭 12 桁だけ)。

### 6.3 クライアント側の照合(任意)
アプリの設定(`app.local.yaml`)に `api.expected_model_sha256_12`(重みの SHA-256 の先頭 12 桁)を書くと、`pipeline/api_preflight.py`(製番処理の事前確認と、運用画面 8765 の動作チェック)が、`/health` の `model.weights_sha256_12` と照合する。
- 一致しない: 「推論 API のモデルが想定の版と一致しません」(製番処理を始めない)。
- 識別情報が無い(旧サーバーなど): 「/health からモデルの識別情報を確認できません」。
- 未設定: 照合しない(従来どおり)。理由に値(ハッシュ・アドレス)は含めない。
- **設定の追記は運用担当が行う**(本実装はアプリの設定を書き換えない)。

## 6.5 Waitress での配信・前景プロセスとしての起動と停止
### 6.5.1 配信と上限(`server` 節。すべて必須・既定値なし)
Werkzeug の開発用サーバーに代えて **Waitress 3.0.2**(`inference_server/requirements.txt` で版を固定)で配信する。上限は設定で明示し、検証する。

| 設定(`server.*`) | Waitress の項目 | 内容・制約 |
|---|---|---|
| `threads`(2〜64) | `threads` | ワーカースレッド数。推論はモデルの安全のため直列なので、増やしても推論は速くならない(`/health` などに答えるため) |
| `max_pending_predict`(1〜`threads`-1) | (アプリ側のセマフォ) | 同時に受け付ける `/predict`(実行中 + 順番待ち)。**`threads` より小さくすることを検証**する(`/health` 用のスレッドを必ず残し、推論中・混雑中も `/health` が答える)。超過は 503 |
| `queue_wait_sec`(1〜600) | (アプリ側) | 推論の順番待ちの上限。超えたら 503(クライアントが再試行できる)。**実行中の推論は中断できない**(Waitress にはハンドラーの実行時間の上限が無い) |
| `backlog`(1〜1024) | `backlog` | listen の受付キュー(OS) |
| `connection_limit`(4〜512、**`threads` + 2 以上**) | `connection_limit` | 同時に開く接続数の上限(受け付けたリクエストのキューもこれで抑える)。Waitress は待受ソケットと内部の trigger も接続数に数えるため、実際に使える接続は `connection_limit` - 2。`/predict` が最大 `threads`-1 件でも `/health` の接続を 1 つ確保できるよう、`threads` + 2 以上を検証する。**ただし、リクエストを送らずに接続だけ保つ相手(keep-alive)が許可リストの中にいれば、その分も接続を使う**(`channel_timeout_sec` で閉じる) |
| `channel_timeout_sec`(5〜600) | `channel_timeout` | リクエストの無い接続を閉じるまで |
| `shutdown_grace_sec`(1〜300) | (アプリ側) | 停止シグナルの後、実行中の推論の完了を待つ上限(§6.5.3) |

固定の上限(コード内): リクエスト本文 16KB・ヘッダー 8KB(超過は 400 / 413 / 431)、`expose_tracebacks=False`(応答にトレースバックを出さない)、`Server` ヘッダーは `sekisan-inference`(Waitress の版を出さない)、
`ipv4=True / ipv6=False`、プロキシヘッダーは信用しない(`clear_untrusted_proxy_headers`。接続元はソケットのアドレスだけ。§4)。
**`timeout_probe_sec` の下限を 0.5 秒から 3 秒へ上げた**のは、本節の機能ではなく、公開前の稼働判定(§5)の誤判定対策による(Windows では、閉じたポートへの接続が「拒否」として返るまで約 2 秒かかることがあり、
それより短いと、拒否(古い設定)をタイムアウト(判定不能。常に拒否)と取り違える)。設定ファイルの `timeout_probe_sec` は 3〜30 秒。
**応答側のタイムアウトは持たない**: 接続・応答の上限は、リクエストの無い接続の `channel_timeout_sec`、推論の順番待ちの `queue_wait_sec`、停止時の `shutdown_grace_sec` で表現する。クライアント(`bs_pkg`)の応答待ち(`api.request_timeout`。省略時は待ち続ける)は別に設定する。

### 6.5.2 起動(前景プロセス)
```
cd inference_server
python prod_server.py check --config prod_server.local.yaml               # 確認(待ち受けも書き込みもしない)
python prod_server.py serve --config prod_server.local.yaml               # 起動(接続設定は書かない)
python prod_server.py serve --config prod_server.local.yaml --publish-config [--replace-stale]   # 接続設定の公開つき(§5)
```
- 前景プロセスとして動く(端末に標準出力、`logging.file` に同じ内容)。**Windows サービス・Linux サービス(systemd など)への登録、起動の自動化、バックグラウンド化は実装していない**(配置先の OS が未決定。§9)。
- 起動の順序: 設定の検証 → モデルの検証とステージング → (`--publish-config` のとき)公開できるかの事前判定 → ポート使用中の確認 → Waitress の待ち受け開始 → モデルの読み込み → (`--publish-config` のとき)接続設定の公開 → **ready**。
  待ち受け開始からモデルの読み込みが終わるまでは、`/health` は 503(`loading`)。

### 6.5.3 停止(前景プロセス)
- **SIGINT(Ctrl+C)・SIGTERM・SIGBREAK(Windows の Ctrl+Break)** で正常終了する。シグナルのハンドラーは停止要求のフラグを立てるだけで、後始末はサーバーのループ側で行う:
  1. 新規の接続の受付を止める(listen ソケットを閉じる)。**新規の接続は拒否される**(接続できない)。すでに開いている接続(keep-alive)に届いたリクエストには、`/health` は `503 stopping`、`/predict` は 503 を返す。
     停止処理への移行と実行中の推論の登録は同じロックで行い、移行の直前に受け付けた推論を数え落とさない。listen ソケットを閉じた後は Waitress のメンテナンス(無通信の接続の整理)が止まるため、停止処理の中で手動で呼ぶ。
  2. **実行中の推論の完了を、`shutdown_grace_sec` まで待つ**(完了した応答は返す)。猶予を超えたら、警告を記録して中断し、停止する。**停止シグナルを 2 回受けたら、猶予を待たずに停止する**(猶予を長くしても強制停止できる)。
  3. 完了した応答を書き切る(出力の残りがなくなるか、2 秒の締切まで)。接続を閉じ、ワーカースレッドを停止し(最大 5 秒)、ステージングしたモデルのコピーを削除して、終了コード 0 で終了する。
- **公開済みの `server.yaml` は削除しない**(現在の安全条件のとおり)。停止後に残るのは「接続を拒否する古い設定」で、クライアントには「接続が拒否されました(API 未起動、または server.yaml の接続先が古い)」と表示される。
  次回の起動で公開するには、既存が古い(接続拒否)ことの確認のうえ `--replace-stale` を明示する。稼働中の別 API の `server.yaml` は、いつでも上書きしない(§5.2)。テストで確認している。
- 強制終了(タスクの強制終了・電源断)では、実行中の推論の出力が一部だけ残ることがある(§7の限界)。`.infer_tmp_*` が残った場合は、手動で削除する。
- モデルの読み込み失敗・公開失敗は、記録して終了する(終了コード 6 / 5。§9.3)。
- **モデルの読み込み中・接続設定の公開中に停止を要求した場合**: 読み込みが終わった後に停止要求を確認し、接続設定の公開も ready もしない(終了コード 0)。停止処理は、読み込み・公開のスレッドの終了を最大 10 秒待ってから終了コードを確定する
  (読み込みが 10 秒を超えて終わらない場合は、警告を記録してそのまま終了する。ステージングのコピーは読み込みスレッドが後始末する)。
  公開を始めた後に停止を要求した場合は、公開は完了する(§5 のとおり、途中で壊れた server.yaml を残さない)。
- 待ち受けを始める前に、シグナルのハンドラーを設置する(待ち受け直後の Ctrl+C を取りこぼさない)。モデルの検証・ステージングの最中の Ctrl+C は、従来どおり中断される。

### 6.5.4 運用ログ(`logging` 節。すべて必須)
- 出力先: **ローカルファイル**(`logging.file`。UNC・出力ルート配下・`server.yaml` の場所は不可。親フォルダは無ければ作る。追記・UTF-8)と標準出力。
- サイズ上限と世代数: `max_bytes`(64KiB〜1GiB)・`backup_count`(1〜100)の `RotatingFileHandler`。`level` は INFO / WARNING / ERROR(DEBUG は不可)。
- 記録する: 起動と停止(停止要求・猶予超過)、モデルの検証・読み込み・ready、接続設定の公開の結果、固定形式のエラー(終了コードの理由)、`/predict` の結果(ページ番号・状態・件数・所要時間。製番・パスは含めない)、
  拒否(許可リスト外・入力検証)。**許可リスト外の拒否は、60 秒に 1 行にまとめる**(件数つき。拒否の洪水でログの世代を埋めない)。接続元が指定できるパス・メソッドは、`/health`・`/predict` の GET/POST 以外は記録しない
  (改行を含むパスによるログの偽造・巨大な行を防ぐ)。
- **記録しない**: パス、接続先アドレス・接続元アドレス、認証情報(トークン)、例外メッセージ、ハッシュ全文(先頭 12 桁だけ)。
  - 本実装のコードは、例外のメッセージを出さず、型名と呼び出し位置(ファイル名・行番号・関数名)だけを記録する。
  - **第二の防御**として、サーバーのログ(`prod_inference_server`・`waitress`・Flask のアプリのログ〔`prod_server`〕・`werkzeug`)のすべてのハンドラーに `RedactingFilter` を付ける。整形後の行から、**改行・制御文字を空白に置き換え**、
    UNC・ドライブ文字・POSIX の 2 階層以上のパス、IPv4 アドレス、`Bearer` / `Authorization` の値、32 桁以上の 16 進文字列を伏せ字にし、1 行を 500 文字までに切り詰め、例外のトレースバックを丸ごと捨てる(Waitress など他のライブラリの出力にも効く)。
  - ログの書き込み・ローテーションの失敗(Windows で別のプロセスがログを開いていて名前を変えられない、など)は、パスを含むトレースバックを出さず、固定の 1 行を 60 秒に 1 回だけ標準エラーへ出す。サーバーは止めない(そのあいだ、ログは記録されない場合がある)。
  - 限界: フィルターは形が決まったものだけを伏せる。例外メッセージ中の固有名のような自由文の秘密、空白を含むパス、相対パス、1 階層だけの POSIX パス、IPv6 アドレス、`Bearer` 以外の形式のトークンまでは保証できない(そのためコードは例外メッセージを出さない)。
    `logging.file` は、出力ルート・`publish.backup_dir`・モデルのフォルダの配下と `server.yaml` には置けない(Windows ではドライブ文字つき。ジャンクション・シンボリックリンクの解決はしない)。
- 配置先でのログの置き場所(権限・世代の保管・転送)は未決定(§9)。

## 6.6 図面解析 AI モデルの管理画面(`prod_admin.py`)
API ホスト上でだけ使うローカル画面。モデル(重み `.pt` と、組になる `model.yaml`)を、**複製・アップロードせずに**選んだ場所のまま参照して、`prod_server.local.yaml` の `model:` 節へ保存する。
既存の画面(運用画面 8765 は製番処理の運用、暫定 API の画面 8771 は暫定 API 用)には本番 API のモデル設定が無いため、別の画面として追加した。

```
cd inference_server
python prod_admin.py --config prod_server.local.yaml [--port 8790]      # http://127.0.0.1:8790/ を開く(この PC のブラウザーだけ)
```
- **LAN からは使えない**: 127.0.0.1 だけで待ち受ける(0.0.0.0 などでは作れない)。接続元・Host・Origin も loopback だけ受け付け、状態を変える操作はカスタムヘッダ(`X-Admin-Request`)と JSON を要求する。
- **使い方**: ① 「モデルファイル(.pt)」欄の初期値は指定の本番モデル(`\\beans-f1\ShareData\estimatic\a_product\model\estimatic_a_20250826.pt`)。「参照…」でこの PC の画面にファイル選択が開く(UNC も選べる)。
  ② 「model.yaml」欄: 空欄なら重みと同じフォルダの `model.yaml` を探す。無ければ「参照…」で選ぶ(別フォルダでよい。コピーしない)。
  ③ 「検証」: 選んだ実ファイルを読み取って、サイズ・SHA-256 を算出し、重みと `model.yaml` の組を検証して、ファイル名・サイズ・ハッシュ先頭 12 桁・判定を表示する。
  ④ 「保存」(検証に通ったときだけ有効): 算出した値を期待値として `model:` 節へ書く(手入力しない)。⑤ 「check を実行」: 読み取り専用の check(`prod_server.py check` と同じ処理)を実行して結果を表示する。
- **`model.yaml` の扱い**(SahiBackend は `model.yaml` を必要とする。読み込み処理は `backends.py` の `SahiBackend`: `model.use_model_type`・`model.my_model`〔重みのファイル名。モデルフォルダ直下〕・`model.threshold`・`model.use_device`・`sahi.*`〔スライス条件〕)。
  重みだけでは保存できない。`model.yaml` が見つからない・読めない・`model.my_model` が**選んだ重みのファイル名と一致しない**場合は、「保存できません」と表示して拒否する。元の `model.yaml` は編集もコピーもしない。
- **my_model の参照名の対応付け(設定用コピー)**: 指定モデルのように、重みと同じフォルダに `model.yaml` が無く、現行の `model.yaml`(`my_model: best.pt`)の参照名が重みの名前(`estimatic_a_20250826.pt`)と違う場合は、
  画面の「my_model の参照名だけを、選んだ重みの名前に置き換えた設定用コピーを作って使う」を**利用者が明示的に選んだときだけ**、次のように対応付ける。
  1. 元の `model.yaml` を読み取り(改行コード・コメント・インデントを含め 1 バイトも変えず)、`model.my_model` の**値だけ**を選んだ重みのファイル名に置き換えた内容を作る(`remap_yaml`)。
  2. 生成前に検証する: 変更が `my_model` の 1 行だけであること、`my_model` を除くすべての設定値(モデル構造・閾値・デバイス・スライス条件・ほかの項目)が元と同一であること。満たさなければ対応付けを中止する。
  3. 画面に**保存前の変更差分**(`- my_model: best.pt` / `+ my_model: estimatic_a_20250826.pt`)と、変わらない値の一覧を示す(「検証」では何も書かない)。
  4. 「保存」で、設定用コピーを `prod_server.local.yaml` と同じ場所の `local_config/<重みの名前>.model.local.yaml` に作る(`*.local.yaml` なので Git 管理外。共有上・UNC には作らない。既存のコピーが違う内容なら退避してから置換。設定の置換に失敗したらコピーも保存前の状態へ戻す)。
  5. `prod_server.local.yaml` の `model:` 節には、`dir`(重みのある場所。**重みは指定の場所を直接参照**し、複製・改名しない)、`yaml_dir`(コピーのあるローカルのフォルダ)、`yaml`(コピーのファイル名)、期待値(重みのサイズ・SHA-256 は**実ファイルから**、`model.yaml` の SHA-256 はコピーから)を書く。
  共有上の `model.yaml`・重み・共有 `server.yaml` は変更しない。API は起動時に、検証した重みとコピーを従来どおり私用の一時フォルダへ検証付きで取り込んで読み込む(ステージングの重みの名前が、コピーの `my_model` と一致する)。
  **この対応付け(コピーの `my_model` = 指定の重みの名前)は、運用担当が指定した重みと現行の `model.yaml` の組み合わせに対する操作で、閾値・デバイス・スライス条件などは現行のまま。** 別の `model.yaml` を使いたい場合は、その `model.yaml` を選ぶ。
  実証(2026-10-29、隔離した一時設定。共有・製番・本番出力・共有 `server.yaml` は未使用): 指定モデル(UNC)+ 現行 `model.yaml` → 保存 → `prod_server.py check` が `ok: true`(モデル検証一致、`cuda:0` / `yolov8`)→ 検証付きステージングから `SahiBackend` の読み込みと合成画像の推論まで成功(torch 2.5.1)。
- **保存**: Git 管理外の `*.local.yaml`(設定ファイルと設定用コピー)だけ。`model:` 節だけを置き換え(ほかの節・コメント・改行コードは保つ)、保存前に同じフォルダへ `prod_server.bak-<時刻>-<PID>.local.yaml` を作り、YAML と `model:` 節の規則を検証してから、一時ファイル + `os.replace` で原子的に置換する。
  共有 `server.yaml` は読み書きしない。モデル設定の保存だけでは、API の起動・再起動・`--publish-config` は行わない。
- **書き込み先の検査(読み取り元とは別)**: 設定ファイル・バックアップ・一時ファイル(設定ファイルのフォルダ)と設定用コピー(`local_config`)は、**実体としてローカルディスクの中**に限る(`require_local_dir`)。
  重み・元の `model.yaml` の**読み取り元は UNC も選べる**が、**書き込みは常にローカルのみ**。検査は、画面の起動時(`prod_admin.py` の起動。不正なら待ち受けずに終了コード 2)、状態表示、保存の開始時、バックアップ・一時ファイル作成の直前、設定用コピーのフォルダの作成直後(作成した階層も含めて再確認。失敗したら作ったフォルダを残さない)に行う。
  1. UNC(`\\\\server\\share`・`//`・`\\\\?\\UNC\\`・`\\\\?\\` を含む)は拒否。ドライブ文字つきの絶対パスだけ。
  2. ドライブの種類(`GetDriveTypeW`)が**固定ディスクでなければ拒否**(ネットワークドライブ・取り外し可能・不明・存在しない・RAM ディスク)。
  3. パスの途中の各階層(存在するもの)が、シンボリックリンク・ジャンクション・マウントポイント等の**再解析ポイントなら拒否**(解決先がローカルでも拒否する。パス文字列だけで判定しない)。まだ無い階層は、親までを同じ基準で確認し、作成後に再確認する。設定ファイル自体がリンクのときも拒否する。
  4. 実体(`realpath`)が UNC または別のドライブへ解決される場合(SUBST・マップ)は拒否し、解決先のドライブの種類も確認する。確認中の例外(権限・I/O)も「ローカルと証明できない」として拒否する。
  5. 拒否のメッセージは固定文(「保存先(設定ファイル・バックアップ・設定用コピー)は、この PC のローカルディスク内に限ります。…」)で、パス・例外メッセージを画面・ログへ出さない。Windows 以外では確認できないため拒否する。
  制約: 再解析ポイントは種類を問わず拒否するため、OneDrive 等のクラウド同期フォルダ配下は使えない(ローカルの通常のフォルダを使う)。
- **漏えい防止**: 応答・画面にはファイル名だけ。ハッシュは先頭 12 桁だけ(全文は設定ファイルにだけ書く)。パスを返すのは「参照…」で選んだ値を入力欄へ入れるときだけ(ローカル画面のみ)。アクセスログは出さない。
  PyTorch のファイルは、先頭の形式(zip / pickle)を見るだけで読み込まない(pickle を実行しない)。
- **check の注意**: `check` は従来どおり読み取り専用だが、設定に `publish.server_yaml` が書いてある場合は、既存の `server.yaml`(共有)を**読み取り**、その接続先へ `/health` を 1 回送る(§5)。共有側に触れたくない間は、`publish` を未設定のままにする(その場合 check は設定エラーで止まる)。
- テスト: `inference_server/tests/test_prod_admin.py`(合成データ・一時フォルダ・loopback。ファイル選択〔runner 差し替え〕・UNC・存在しないファイル・不正形式・`model.yaml` の不一致・サイズ/SHA 自動取得・保存・check・LAN 拒否・非漏えい)。

## 7. `/predict` の入力検証と出力
- `page_nmb`: 数字 1〜6 桁。`extension`: `png`・`jpeg`・`jpg`。
- `work_dir`: 絶対パスで、**設定の `output_root` の直下の製番フォルダ**(製番は英数字 4〜20 文字)。`..`・NUL・出力ルート自身・入れ子のフォルダ・別の場所・リンク/ジャンクションで別の場所を指すものは **400**。画像も通常ファイルでリンクでないこと。
- 結果は、製番フォルダ内の一時フォルダ(`.infer_tmp_<乱数>`)へ書いてから置き換える(可視化画像 → 検出テキストの順)。推論の失敗では、既存のファイルを変えず、一時フォルダも残さない。同一ページの同時書き込みは排他。
  置き換えの直前に、製番フォルダが検証後にリンクへ差し替えられていないことを再確認する。
  **限界**: 置き換え(`os.replace`)自体が共有の障害で失敗した場合、可視化画像だけ新しくなることがある(製番処理は失敗として扱われ、失敗時の後始末で製番フォルダごと削除される)。プロセスの異常終了で `.infer_tmp_*` が残ることがある(起動時の掃除はしない。共有の走査を避けるため)。
  ハードリンクは検出できない(出力共有への書き込み権限を持つ者は信頼する前提)。
- 失敗の応答は `推論に失敗しました: <例外の型名>` だけ。応答の `text_file_path` は、クライアントが送った `work_dir` の表記(検証済み)に `<ページ>_detected.txt` を付けたもの(別名表記の UNC を返さない)。
- 同時に受け付ける `/predict` は 8 件まで(超過は 503)。推論は直列。
- 本文は 16KB まで(超過は 413)。

| モデルの版の記録(期待値の SHA-256・サイズ)と、共有のモデルファイルとの照合 | **未確認**(手元の旧モデルと共有のモデルは同サイズだが、ハッシュは未照合) |
| **サービス化・起動の自動化**(Windows サービス / Linux の systemd など)・再起動時の自動起動・異常終了時の再起動 | **未決定・未実装**(配置先の OS が未決定。前景プロセスとしての起動・停止だけを実装した。§6.5) |
| **TLS**(HTTPS)・**プロキシ**の扱い(クライアントのプロキシ経由の可否、サーバーから見える接続元、許可リストへの追加の可否。§4) | **未決定**(現状は HTTP のみ。TLS は未実装) |
| 許可クライアント(`allowed_clients`)の実値・待受アドレス(`bind.host`)・ポートの実値 | **未決定**(設定ファイルに明示する。サンプルは文書用の予約アドレス) |

| 実図面での検出結果の妥当性(実モデルでの確認) | 未検証(自動テストは fake バックエンド) |

### 9.2 手順
1. 配置先に推論用 venv を用意する(`inference_server/requirements.txt`〔Waitress・Flask・Werkzeug・PyYAML・requests を固定〕と `requirements-real.txt`〔sahi・ultralytics・torch など〕。torch は **2.5.1+cu124**: `requirements-real.txt` の固定。2.6.0+cu124 では実モデルを読み込めない。`inference_server.md` §9)。
2. `prod_server.local.yaml` を作る(§8)。期待ハッシュは、管理担当が控えた記録から転記する。
3. **確認(書き込みなし)**: `python prod_server.py check --config prod_server.local.yaml`。`ok: true`、`model.verified: true`、`publish_plan` の内容(どのキーが変わるか。値は出ない)を確認する。
4. **公開なしで起動(前景プロセス)**: `python prod_server.py serve --config prod_server.local.yaml`(端末を開いたまま)。モデル読み込み後に、許可された接続元から `/health` が 200 になることを確認する(許可外の接続元から 403 になることも確認)。この時点では共有 `server.yaml` は変わらない。
5. **接続設定の公開**(定期実行・手動実行が無いことを確認してから): 停止して、`--publish-config`(既存が古いときは `--replace-stale`)を付けて起動する。終了コード 5 のときは、理由(稼働中の別 API / 既存が読めない / 古い設定で `--replace-stale` が無い)を確認する。
6. 運用画面 8765 の動作チェックで、推論 API が OK であることを確認する。必要なら `api.expected_model_sha256_12` を設定する(§6.3)。
7. 1 製番だけを手動で実行し、生成物と画面を確認する(タスクの扱いは §9.1 の最初の行)。
8. **停止**: 起動した端末で Ctrl+C(Windows は Ctrl+Break も可)、または SIGTERM。実行中の推論の完了を `shutdown_grace_sec` まで待ってから終了する(§6.5.3)。ログに「停止しました」が出て、終了コードが 0 であることを確認する。
9. 戻す場合: API を停止し、`backup_dir` の退避ファイルを `server.yaml` へ戻す。

### 9.3 終了コード
| コード | 意味 |
|---|---|
| 0 | 正常終了(停止シグナル) |
| 2 | 設定の不備(`ConfigError`)・トークンファイルの不備 |
| 3 | ポートを待ち受けできない(使用中・ワイルドカードで待ち受ける別のサーバーがある・Waitress が無い・待受アドレスが設定と一致しない など) |
| 4 | モデルの検証失敗(期待値と不一致・欠落) |
| 5 | 接続設定を公開できない(`--publish-config` の条件を満たさない・書き込みの失敗)。待ち受け前・読み込み後のどちらでも、この終了コードで停止する |
| 6 | バックエンド(モデル)の読み込みに失敗した(CUDA・依存関係など)。API は停止する |
| 7 | サーバーのループで想定外の失敗が起きた(ログには型名と呼び出し位置だけ記録) |
| `check` | 0: 問題なし / 1: 要確認(アドレス未割当・ポート使用中・出力ルート無し・モデル不一致) |

## 10. テスト
