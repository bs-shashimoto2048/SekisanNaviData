# 運用設定・実行管理画面(`ops_console.py`)

製番処理の運用に必要な最小の操作を、ローカルの画面からまとめて行う。処理そのものは既存の `app.main()` をそのまま呼ぶ(処理ロジックを別実装しない)。

## 起動

```
.venv\Scripts\python.exe ops_console.py serve [--port 8765] [--config <app の設定ファイル>]
```

- 待ち受けは **127.0.0.1 だけ**(他のアドレスは指定できない)。ブラウザで `http://127.0.0.1:8765/` を開く。
- `--config` 省略時は `app.local.yaml`(無ければ `app.yaml`)。サンプルのままの設定では、動作チェックが NG になり、製番処理も起動時にエラーになる(従来と同じ)。
- 状態を変える操作(保存・実行・タスク登録/解除)は、別サイトからの送信を防ぐためカスタムヘッダを要求し、Host ヘッダが 127.0.0.1 / localhost のものだけを受け付ける。

## 画面(左に 1〜4、右に 5)

| 項目 | 内容(項目名は仮) |
|---|---|
| 1. 運用設定 | 出力先(絶対パス。空なら設定ファイルの `data.output`)。**参照… / 保存 / 再読込** |
| 2. 動作チェック | 設定形式・出力先・変換ソフト・設計サーバー参照先・ホスト DB(読み取り専用の照会)・推論 API(`/health` だけ)を確認して結果を表示。**製番処理や `/predict` は呼ばない。何も書かない** |
| 3. 定期実行(タスクスケジューラ) | 有効/無効・開始時刻(HH:MM)・間隔(日。既定 2 = 1 日置き)。**タスクを登録・更新 / 解除** は、この画面で押したときだけ実行 |
| 4. 製番を指定して実行 | 製番(1 件)と出力先を指定して **1 回実行**。実行中は開始できない |
| 5. 実行履歴 | 日時・種別(手動/定期)・製番・状態(実行中/完了/失敗/スキップ)・理由 |

- **出力先の「参照…」**: この PC のフォルダ選択ダイアログ(標準のフォルダ選択。**新しいフォルダの作成ボタンなし**・「マイ コンピューター」起点)で、**既存のローカルフォルダ**を選ぶ。ブラウザーは選んだフォルダの絶対パスを渡せないため、**ダイアログは 127.0.0.1 のサーバー側(この PC の画面)に表示**し(`ops/folder_picker.py`、PowerShell の `FolderBrowserDialog`)、選ばれた絶対パスを出力先欄に入れる(`POST /api/settings/browse-folder`。ほかの状態を変える操作と同じく、カスタムヘッダと 127.0.0.1 / localhost の Host だけを受け付ける)。
  - 選ぶだけでは**保存しない**(「保存」で `ops.local.yaml` に保存、「再読込」で復元。既存の保存・検証の処理のまま)。**キャンセルしたときは入力欄を変えない**。フォルダやファイルは作成・変更しない。
  - **UNC(`\\サーバー\共有名\…`)とネットワークドライブは選べない**(固定文言「ネットワーク上の場所は選べません」。ドライブの種類で判定)。絶対パス・`..` なし・既存フォルダ、という既存の出力先検証も通す。手入力の出力先の検証と実行時の安全条件は変えない。
  - ダイアログは同時に 1 つだけ(開いている間の再要求は 409)。エラーの文言にパスは含めない。パスをログ・履歴に残さない。
  - 4. 「製番を指定して実行」の出力先は、**空ならこの 1. の出力先**を使う(従来どおり)。
- **動作チェックの推論 API(`/health`)**: 判定は、製番処理の事前確認(`pipeline/api_preflight.py`、下記「推論 API の事前確認」)と**同じ関数**で行う(`ops/checks.default_health_check`)。**画面の「推論 API(/health)」が OK なら、同じ設定で製番処理の事前確認も通る**(接続先・プロキシ・リダイレクト・タイムアウトが同一)。
  - 接続先: 製番処理(Step.4 の `/predict`)と同じ API 設定ファイル(`api.dir_venv` / `api.yaml_file` の `server.yaml`、`host.pc_ip`・`host.port`)。
  - **プロキシ**: `/predict` と同じ決め方(`api.use_proxy`〔省略時 true〕と `server.yaml` の `proxy.host` / `proxy.port`)。**画面だけプロキシなしにはしない**(従来の画面はプロキシなし固定で、結果が事前確認と食い違い得た)。
  - **リダイレクトは追跡しない**(最初の応答が HTTP 200 のときだけ OK。3xx は NG)。待ち時間は `api.health_timeout`(既定 5 秒)。
  - 設定の欠落(`server.yaml` が無い・読めない・項目不足、`api` の設定項目なし)・接続拒否・タイムアウト・HTTP 200 以外は、**NG**(`server.yaml` が無いときも SKIP にしない)。理由は事前確認と同じ固定文言で、**接続先(ホスト名・ポート・URL)・パス・認証情報・例外メッセージは画面に出さない**(例外型と HTTP 応答コードだけ)。
  - **本番モード**(`app.yaml` / `app.local.yaml`。`inference_server` の節なし): `app.main` は推論サーバーを起動しない。**共有の `server.yaml` が示す API を、別途起動しておく必要がある**。未起動だと `/health` は NG になり、製番処理は事前確認の時点で開始されない。
  - **統合モード**(検証設定。`inference_server.enabled: true`): `app.main` が `127.0.0.1` 限定のサーバーを起動して `server.yaml` を出力ルート配下に書き、停止時に削除する。**`server.yaml` は起動中だけ存在する**ため、この設定(統合モード)の動作チェックは**常に SKIP**(`app.main` も事前確認を呼ばない。起動時に準備完了を確認する)。
  - 接続が拒否されたとき(待ち受けるプロセスがない)は、NG に「API が未起動、または server.yaml の接続先が古い可能性」を添えて表示する。それ以外の失敗には、この案内を付けない。
  - この PC での暫定・隔離運用(専用設定 `app_interim.yaml`、起動スクリプト `tools/run_interim_api.ps1`)は `docs/inference_api_interim_operation.md`(製番の指定実行・全製番の仮定期実行は §16、全件処理の実績と暫定運用の手順は §17)。
- 文字は 22px(本文)・24px(見出し)、入力欄とボタンは高さ 48px。**表示領域の高さが約 950px 以上(1920×1080 のブラウザなど)なら、スクロールなしで全項目が見える**。それより低い画面(1536×864・1366×768 など)では、左の 1〜4 だけが内側でスクロールし(項目が重なったり欠けたりはしない)、履歴は右で幅いっぱいに表示される(幅が足りないときは履歴だけ横スクロール)。画面幅 1500px 以下では左の列を少し細くする。

## 製番の指定実行

**起動後のコード更新の検出(古いコードのままの常駐プロセスで処理しない)**: 8765 は長く動かす常駐プロセスで、Python は起動時にモジュールを読み込む。作業ツリーが後から新しいコミットへ進んでも、動いているプロセスは起動時のコードのままになる
(2026-10-30 の本番 1 件試験は、10/26 起動の 8765 が、その後に統合された表示用プレビュー〔`__preview.png`〕・書類の名前〔`0_S0` / `0_A1`〕の実装より古いコードで処理し、警告なしにプレビューの無い出力を本番出力先へ作った)。
そこで、起動時の作業ツリーのコミット(`.git` の HEAD。git のプロセスは起動しない)を記録し、**手動実行の開始前**(履歴・ロック・フォルダ作成・印刷・API 呼び出しより前)と**動作チェック**で現在の HEAD と比べる(`ops/code_version.py`)。
更新されていれば、手動実行は**固定の理由**(短縮した SHA だけ。「運用画面を再起動してから実行してください」)で拒否し、動作チェックの「実行中のコードの版」は NG になる。git が読めない場合は「確認できない」(スキップ)として止めない。
暫定運用(interim)・開発用は対象外(定期実行は、`run_scheduled_host` と今すぐ実行が同じ照合を通す。→「定期実行と「今すぐ実行」」)。比べるのはコミットだけで、未コミットの変更は見ない。

**出力先の整合確認(本番推論 API との一致)**: 製番フォルダは `<出力ルート>/<data.storage>/output/<製番>` に作られる(`pipeline/settings.py`・`app.py`)。本番推論 API は、その親フォルダ(`<data.output>/<data.storage>/output`)を `output_root` として、**直下の製番フォルダだけ**を受け付ける。
出力先欄(空なら 1. 運用設定の出力先 `ops.output_root`)が、設定の `data.output` と違う場所を指すと、製番フォルダ・印刷・CAD 変換が先に行われ、最後の API 呼び出しだけが拒否される。
そこで、**手動実行(4.)は、実行を始める前**(履歴・ロック・スレッド・フォルダ作成より前)に、`app.main(output_root=…)` と同じ規則で算出した実効の出力先が、設定の `data.output` から算出した本番の出力先と一致することを確認し、違えば**固定の理由で拒否する**(`ops/output_guard.py`。別の場所へ黙ってフォールバックしない)。
- 一致する指定(欄に `data.output` と同じ値。区切り・大文字小文字・末尾の区切りは区別しない)は、従来どおり実行する。欄も運用設定も空なら、従来どおり `data.output` を使う(設定は読まない)。
- 欄が空で運用設定の出力先が違う場合も拒否する(欄に `data.output` と同じ値を明示すれば、その指定で実行できる)。
- **暫定運用(interim)・開発用の設定は変更しない**(ガードは `ops_console.build_context` の手動実行と、定期実行・今すぐ実行の `run_scheduled_host` / `start_run_now` にだけ接続)。
- 解消するには、運用設定(1.)の出力先を空にするか `data.output` と同じ値にする(運用設定の変更。コードとは別)。

`app.main(config_path, products=[製番], output_root=出力先)` を呼ぶ。`products` を省略した従来の呼び出し(`app._cli`・定期実行)は変わらない。指定時は **ホストの製番一覧取得を省き**、その製番を既存の製番処理(`run_product`)に通す。対象判定・処理済み判定(出力先に既にあればスキップ)・失敗時の後始末は、製番処理の中で従来どおり行われる。

- 状態は `app.main` の結果をそのまま反映する: 完了 → **完了**、失敗 → **失敗**(理由つき)、処理済み・対象外 → **スキップ**(完了とは扱わない)、例外 → **失敗**。
- **推論 API の応答待ち(`api.request_timeout`、任意)**: `app.local.yaml` の `api.request_timeout`(秒)で、本番モードの `/predict` の応答待ちを設定できる。**省略すると従来どおり待ち続ける**(既定値なし。値は本番ログの実測に基づいて別途決める)。不正値(0・負・数でない値・float で表せない非常に大きな整数など)は、製番処理の開始前にエラーとなり、動作チェックの「設定の形式」も NG になる。超過した製番は、既存の失敗の扱い(失敗として記録・製番フォルダを削除・再試行なし)になる。詳細は `docs/inference_contract.md` §6。
- **推論 API のモデルの版の照合(`api.expected_model_sha256_12`、任意)**: `app.local.yaml` に重みの SHA-256 の先頭 12 桁を書くと、事前確認と動作チェックが `/health` の `model.weights_sha256_12`(本番推論 API `inference_server/prod_server.py` が返す。[production_inference_api.md](production_inference_api.md) §6.3)と照合し、違う版のモデルでは製番処理を始めない。未設定なら照合しない。
- **推論 API の事前確認**: 本番モード(推論サーバーを自分で起動しない設定)では、`app.main` が重い処理(ホスト照会・設計データ・印刷・変換・画像作成)に入る前に、推論 API の `/health` を 1 度だけ確認する(通常処理・指定実行とも)。リダイレクトは追跡せず、最初の応答が HTTP 200 のときだけ「使える」とする。使えないとき(`server.yaml` が無い・読めない、接続拒否、タイムアウト、HTTP 200 以外(リダイレクトを含む))は、製番処理を始めず、履歴に「**失敗**」と理由(「推論 API を利用できないため、製番処理を開始しませんでした(…)」。接続先は含まない)を記録する。通常処理は「(全体)」、指定実行は指定した製番として失敗にする(完了・スキップ扱いにしない)。詳細は `docs/inference_contract.md` §2。統合モードと `run-scheduled --dry-run` の動作は変わらない。
- **二重起動の防止**: ロックファイルへの OS のファイルロック(排他)で、画面からの実行どうし、および画面とタスクスケジューラからの定期実行の間で排他する。実行中の開始は拒否される(画面では 409 の旨を表示、ボタンも無効)。ロックは持ち主のプロセスが終了(異常終了を含む)すれば OS が解放するため、古いロックは残らず、PID の使い回しも問題にならない。状態確認が一瞬ロックを取る間と重なっても、取得は短く再試行する。
- **`SystemExit`(`design_mod` の `sys.exit()` など)**: `app.main` の中で `SystemExit` が出ても、履歴は「**失敗**」で終わる(「実行中」のまま残らず、完了・スキップ扱いにもしない)。理由は固定の「処理が途中で終了しました(SystemExit)」で、終了コードやメッセージ(パス・秘密情報を含みうる)は記録しない。COM の終了処理とロックの解放は従来どおり行い、定期実行(`run-scheduled`)は終了コード 1 になる。製番フォルダ(部分出力)は、`app.main` 側の製番処理が既存の失敗と同じ後始末(出力ルート配下に限る削除)を行う(`docs/refactor_plan.md` §6)。`run-scheduled --dry-run` は `app.main` を呼ばないため影響しない。
- 画面を開き直したとき、終わりが書かれず「実行中」のまま残った履歴は「失敗(処理が途中で終了)」にする(プロセスが強制終了された場合など)。
- **COM の初期化・終了**: ホスト DB(`host_mod`)は COM(ADODB)を使う。メインスレッド以外では COM が未初期化で、`ADODB.Connection` の生成が `0x800401F0` で失敗し、`host_mod` は例外を握りつぶして「ホスト情報を取得できません」(スキップ)にしてしまう。そのため、**製番の実行(`ops-run` の worker スレッド。定期実行も同じ処理)** と **動作チェックのホスト照会(HTTP の要求スレッド)** は、呼ぶ前に同じスレッド内で `CoInitialize`、終わったら必ず `CoUninitialize` を呼ぶ(`ops/com.py`)。
  - 初期化に失敗したときは `app.main` を実行せず、履歴に「失敗(COM を初期化できないため実行しませんでした)」を残す(終了処理は呼ばない)。
  - 終了処理(`CoUninitialize`)が例外になっても、握って無視する。すでに決まった実行結果(完了・失敗・スキップと理由)は変えない。

## 定期実行(Windows タスクスケジューラ)と「今すぐ実行」

登録されるタスク(名前 `SekisanNaviData_Ops`)は、**N 日ごと**(画面の「間隔」。**2 = 1 日置き(既定)**、1 = 毎日)の指定時刻に、次を 1 回起動するだけ。

```
<python> ops_console.py run-scheduled [--config ...]
```

画面の「3. 定期実行」には、タスクの登録とは別に **「今すぐ実行」ボタン**がある。次回の実行時刻を待たず、同じ定期処理を直ちに 1 回開始する。**タスクの登録・有効/無効・開始時刻・間隔は、このボタンでは一切変更しない**(タスクが未登録・無効でも実行できる)。

### 共通の仕様(定期実行と「今すぐ実行」は、同じ関数・同じ条件で動く)

- **対象は、実行のたびにホスト DB を読み取り専用で照会して確定する**(`ops/host_targets.py`)。固定の製番リスト・前回の対象は使わない(旧: 設定の `scheduled_products` の明示リスト〔PR #43〕は**撤回**した。`ops.local.yaml` に残った古いキー `scheduled_products` / `scheduled_max_products` / `scheduled_max_minutes` / `scheduled_retry_products` は無視され、次の保存で消える)。
  - 対象 = 「実行月(当月)に **3 番図面が出図済み**」かつ「製番が設定の `target_initial`(**A1**)で始まる」製番のうち、
    - 出力先に製番フォルダが**無い**もの(未処理)、または
    - 出力先に製番フォルダがあっても、**未完了マーカーがある**もの(再処理)。
  - **「当日まで」の日付上限は設けない。** 通常バッチ(`host_mod.create_n3_design_list` → `HostAccess.search_design3`)の SQL も、3 番図面出図日の**年・月だけ**で絞っており、日の条件はない(ログの「当月(～当日)」は表記のみ)。この既存ルールを変えず、定期実行・「今すぐ実行」も**文字まで同じ SQL** で照会する(出図日が実行日より後の行がホストにあれば、通常バッチと同様に対象へ含まれる)。
  - 並びは通常バッチと同じ: 未処理は昇順、未完了マーカーのある再処理対象はその後ろに加わる。
  - 出力済みで未完了マーカーが無い製番は除く(処理済み)。**件数・時間の上限はなく、取得した対象はすべて処理する。**
  - ホスト一覧の取得は `bs_pkg.host_mod` と同じ接続・同じ SELECT(読み取り専用。更新系の SQL は発行しない)。`host_mod.create_n3_design_list` は失敗を握りつぶして「出図なし」と同じ空のリストを返すため使わず、**失敗は例外にして**「0 件成功」と区別する。出図が 1 件も無い月は、正常な「対象なし」(履歴は**スキップ**)。
  - 出力先を読めないとき(フォルダが無い・アクセス不可)は、全製番が未処理に見えて再処理してしまうため、対象を確定せず失敗にする。
- **全体の安全条件**を満たさなければ、**製番処理を始めず、0 件成功にもせず、履歴に「失敗」と理由を残す**(画面にも出る)。順序: 運用設定の読込 → 実効出力先の照合(`OutputGuard`。設定 `data.output` の下の `storage/output` と一致) → 起動時のコード版の照合(`CodeVersionGuard`) → COM の初期化 → ホストの照会(対象の確定)→ 推論 API の事前確認(`app.main` が製番処理の前に 1 度だけ。使えなければ全対象を「未開始」にして失敗)。Interim(暫定運用)・検証用の設定へはフォールバックしない。
- **処理**は `app.main(products=対象, output_root=…)` をそのまま呼ぶ(処理ロジックを二重に持たない)。**製番ごとの通常例外・`SystemExit` は、その製番の失敗として記録・後始末され、残りの製番の処理が続く**(`pipeline.product_flow.run_product`)。**全対象を試した後、失敗が 1 件でもあれば、実行全体を「失敗」**として記録する(`run-scheduled` の終了コードは 1)。
- **実行ロック**(`ops_run.local.lock`。OS のファイルロック)は共通。他の実行(手動・定期・今すぐ実行・検証)が動作中なら開始しない: 「今すぐ実行」は 409(「すでに実行中です」。履歴は作らない)、定期実行は履歴に「スキップ(実行中のため開始しませんでした)」を残す。ロックは、完了・失敗・例外・`SystemExit` のどれでも解放される。
- **履歴**: 種別は定期実行が「**定期**」、「今すぐ実行」が「**今すぐ実行**」、`--dry-run` が「**定期(検証)**」。対象(`targets`)は実行前に記録し、完了後は製番ごとの結果(`results`: 完了 / 失敗 / スキップ / 未開始)を残す。実行全体の中断・失敗(推論 API の事前確認の失敗、実行全体の例外、COM 初期化失敗)は、製番ごとの `scope: run` を付けて区別する。
- **ホスト DB・出力先・API・製番範囲は、「今すぐ実行」専用には変えない**(定期実行と同じ設定・同じ経路)。

### 「今すぐ実行」ボタン(画面と HTTP)

- 押下すると**確認ダイアログ**が出る。「当月の3番図面出図・initials=A1・未処理または未完了マーカーあり」の製番をこの時点でホストから取得して処理すること、**本番の出力が作成される**こと、件数・時間の上限がないこと、タスクの設定は変わらないことを明記する。同意すると `POST /api/run-now`(本文 `{"confirmed": true}`)を送る。
- 要求は他の状態変更と同じく、**127.0.0.1 限定・Host ヘッダ検査・カスタムヘッダ `X-Ops-Request`**(別サイトからは送れない)を要求し、さらに本文の `confirmed: true`(確認ダイアログへの同意)がなければ 400 で拒否する(何も始めない)。
- 受理されると、対象の確定(ホストの再照会)と処理は別スレッドで行い、画面は直ちに戻る。**実行中はボタンを無効にして「実行中」と表示**する。完了後は、**完了・失敗・スキップ・未開始の件数と製番ごとの結果**を「3. 定期実行」の欄に表示する。
- 画面を再読み込みしても、**ロックの状態(実行中か)と運用履歴(`/api/history`)から、実行中の状態・直近の結果を復元**する。
- 他の実行が動作中なら、画面に「すでに実行中です。完了してから開始してください。」と表示する。

### 定期実行(`run-scheduled`)

- `run-scheduled` は、上の共通の仕様どおりに、ホストから対象を取得して処理し、結果を履歴に「定期」として残す。出力先を 1. で保存していれば、その出力先で実行する。
- **検証用 `--dry-run`**: `ops_console.py run-scheduled --dry-run` は、タスクの起動経路を安全に確認するための入口。**本番と同じ全体の検査と、同じ対象の確定(ホストの読み取り専用の照会)**までを行い、**`app.main` は呼ばない**(製番処理・設計データ・共有・API・CAD には触れない)。履歴には種別「**定期(検証)**」・製番欄「(検証のみ)」で、確定した対象を `targets` に記録する。標準出力に、検査の結果・今回の対象・登録済みタスクの起動先(このコードの場所と一致するか)を表示する。
  - 状態: 完了(検査に合格)/ 失敗(全体の条件を満たさない・ホスト一覧を取得できない。理由は固定文で履歴にも残る)/ スキップ(他が実行中のため二重起動の防止)。終了コードは、失敗のときだけ 1。
  - 画面の「3. 定期実行」が登録するタスクのコマンドは変わらない(`--dry-run` は付かない)。
- **従来の全件処理(`RunManager.run_scheduled` / `run_scheduled_dry_run`)は、暫定運用(interim)が共有しているため変更していない**。`ops_console.py` の定期実行と「今すぐ実行」だけが、新しい `run_scheduled_host` / `start_run_now` / `run_scheduled_host_dry_run` を使う。
- 登録・更新(`schtasks /Create … /F` と `/Change /ENABLE|/DISABLE`)と解除(`/Delete`)は、画面の明示操作でだけ実行する。表示のための照会(`/Query`)は読み取りだけ。
- **実行間隔**: 既定は **2 日 = 1 日置き**(`/SC DAILY /MO 2`)。画面の「間隔」(1〜30 日)で変更できる(1 = 毎日)。対象は「当月の出図済み製番 − 出力先にある処理済み製番(未完了マーカーのあるものを除く)」なので、間隔を変えても取りこぼしは起きず、処理が始まるまでの遅れとホスト照会の頻度が変わるだけ。
- **制約(初期版の仕様)**: タスクは、このコンピューターの**ログオン中のユーザーとして、ログオン中だけ**動く(`/RU` を付けない通常のタスク)。**ログオフ中は動かない**。この制約は画面(「3. 定期実行」の注記)にも表示する。**ログオフ中の実行を可能にする設定(パスワード保存の `/RU`・`/RP` など)は、初期版では追加しない。**
- **作業フォルダ**: タスクの既定の作業フォルダは System32 のため、`ops_console.py`(`serve`・`run-scheduled`)が起動直後にリポジトリのフォルダへ移る。設定の相対パスは、そこを基準に読む。
- **コマンドの引用**: `<python>`・`ops_console.py`・`--config` のパスはそれぞれ二重引用符で囲む(空白を含むフォルダでも動く)。`schtasks /TR` の上限(261 文字)を超えるときは、登録せずにエラーを表示する。
- **登録済みタスクの起動先**: `TaskScheduler.action_target_state()` が、`schtasks /Query`(読み取りのみ)で、タスクが起動する `ops_console.py` と Python が、このコードの場所と一致するかを照会する(`--dry-run` が表示)。**タスクの作成・変更・有効化はしない**。
- テストでは `schtasks` の実行(`runner`)・ホスト DB(`fetch`)をモックし、`subprocess.run` が呼ばれたら失敗にする。**開発・テストでこの PC の実タスクは登録・変更・削除せず、実 DB・本番出力も使わない。**(`tests/test_ops_run_now.py`)

## 起動・停止バッチ(`start_ops_console.bat` / `stop_ops_console.bat`、実体は `ops_ctl.py`)

常駐の 8765 を、手でコマンドを打たずに起動・停止するための手順。サービス・タスク・スタートアップへは登録しない(手で実行する)。

```
start_ops_console.bat [--port 8765] [--config <app の設定ファイル>]
stop_ops_console.bat  [--port 8765]
.venv\Scripts\python.exe ops_ctl.py status [--port 8765]
```

- Python は、環境変数 `OPS_PYTHON`(あれば)→ このフォルダの `ops_python.local.txt` の1行目(任意・Git 管理外。`.venv` の無い作業ツリーで、本体の `.venv\Scripts\python.exe` のフルパスを書いておく。ダブルクリックでも環境変数なしで使える)→ このフォルダの `.venv\Scripts\python.exe` の順。どれも無い/ファイルが存在しなければ、起動せずにエラーで終わる(別の Python は使わない)。**バッチを置いた作業ツリーの `ops_console.py` を起動する**ので、設定(`ops.local.yaml`・`app.local.yaml`)・履歴もその作業ツリーのものになる。
- 起動: ポートが使用中なら起動しない(使っているプロセスは止めない)。起動したら PID とプロセス作成時刻を `ops_console.local.pid`(Git 管理外)に記録し、`/api/state` が 200 を返し、待受が自分のプロセスになったことを確認する。
- 停止: 記録した PID が「作成時刻・コマンドライン(この場所の `ops_console.py serve --port N`)まで一致」し、待受ポートの持ち主が自分のプロセスのときだけ、そのプロセスと子(venv の起動ランチャーと実体)を止める。**名前(python.exe)での一括終了はしない。記録の無いプロセス(手で起動した 8765 など)は止めない。**
- 製番処理・定期実行・検証の実行中(実行ロック `ops_run.local.lock` が取られている)、または実行中かを確認できないときは、停止しない。
- 待機は `ping -n`(`timeout` は標準入力が閉じていると失敗するため使わない)。
- 手で起動した既存の 8765 をこのバッチの管理下へ移すには、いったんそのプロセスを手で終了(PID・作業ツリー・実行中でないことを確認)してから `start_ops_console.bat` で起動する。
