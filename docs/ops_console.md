# 運用設定・実行管理画面(`ops_console.py`)

製番処理の運用に必要な最小の操作を、ローカルの画面からまとめて行う。処理そのものは既存の `app.main()` をそのまま呼ぶ(処理ロジックを別実装しない)。

## 起動

```
.venv\Scripts\python.exe ops_console.py serve [--port 8765] [--config <app の設定ファイル>]
```

- 待ち受けは **127.0.0.1 だけ**(他のアドレスは指定できない)。ブラウザで `http://127.0.0.1:8765/` を開く。
- `--config` 省略時は `app.local.yaml`(無ければ `app.yaml`)。サンプルのままの設定では、動作チェックが NG になり、製番処理も起動時にエラーになる(従来と同じ)。
- 状態を変える操作(保存・実行・タスク登録/解除)は、別サイトからの送信を防ぐためカスタムヘッダを要求し、Host ヘッダが 127.0.0.1 / localhost のものだけを受け付ける。

## 画面(左に 1〜4、右に 5)

| 項目 | 内容(項目名は仮) |
|---|---|
| 1. 運用設定 | 出力先(絶対パス。空なら設定ファイルの `data.output`)。**保存 / 再読込** |
| 2. 動作チェック | 設定形式・出力先・変換ソフト・設計サーバー参照先・ホスト DB(読み取り専用の照会)・推論 API(`/health` だけ)を確認して結果を表示。**製番処理や `/predict` は呼ばない。何も書かない** |
| 3. 定期実行(タスクスケジューラ) | 有効/無効・開始時刻(HH:MM)・間隔(日。既定 2 = 1 日置き)。**タスクを登録・更新 / 解除** は、この画面で押したときだけ実行 |
| 4. 製番を指定して実行 | 製番(1 件)と出力先を指定して **1 回実行**。実行中は開始できない |
| 5. 実行履歴 | 日時・種別(手動/定期)・製番・状態(実行中/完了/失敗/スキップ)・理由 |

- **動作チェックの推論 API(`/health`)**: 判定は、製番処理の事前確認(`pipeline/api_preflight.py`、下記「推論 API の事前確認」)と**同じ関数**で行う(`ops/checks.default_health_check`)。**画面の「推論 API(/health)」が OK なら、同じ設定で製番処理の事前確認も通る**(接続先・プロキシ・リダイレクト・タイムアウトが同一)。
  - 接続先: 製番処理(Step.4 の `/predict`)と同じ API 設定ファイル(`api.dir_venv` / `api.yaml_file` の `server.yaml`、`host.pc_ip`・`host.port`)。
  - **プロキシ**: `/predict` と同じ決め方(`api.use_proxy`〔省略時 true〕と `server.yaml` の `proxy.host` / `proxy.port`)。**画面だけプロキシなしにはしない**(従来の画面はプロキシなし固定で、結果が事前確認と食い違い得た)。
  - **リダイレクトは追跡しない**(最初の応答が HTTP 200 のときだけ OK。3xx は NG)。待ち時間は `api.health_timeout`(既定 5 秒)。
  - 設定の欠落(`server.yaml` が無い・読めない・項目不足、`api` の設定項目なし)・接続拒否・タイムアウト・HTTP 200 以外は、**NG**(`server.yaml` が無いときも SKIP にしない)。理由は事前確認と同じ固定文言で、**接続先(ホスト名・ポート・URL)・パス・認証情報・例外メッセージは画面に出さない**(例外型と HTTP 応答コードだけ)。
  - **本番モード**(`app.yaml` / `app.local.yaml`。`inference_server` の節なし): `app.main` は推論サーバーを起動しない。**共有の `server.yaml` が示す API を、別途起動しておく必要がある**。未起動だと `/health` は NG になり、製番処理は事前確認の時点で開始されない。
  - **統合モード**(検証設定。`inference_server.enabled: true`): `app.main` が `127.0.0.1` 限定のサーバーを起動して `server.yaml` を出力ルート配下に書き、停止時に削除する。**`server.yaml` は起動中だけ存在する**ため、この設定(統合モード)の動作チェックは**常に SKIP**(`app.main` も事前確認を呼ばない。起動時に準備完了を確認する)。
  - 接続が拒否されたとき(待ち受けるプロセスがない)は、NG に「API が未起動、または server.yaml の接続先が古い可能性」を添えて表示する。それ以外の失敗には、この案内を付けない。
  - この PC での暫定・隔離運用(専用設定 `app_interim.yaml`、起動スクリプト `tools/run_interim_api.ps1`)は `docs/inference_api_interim_operation.md`(製番の指定実行・全製番の仮定期実行は §16、全件処理の実績と暫定運用の手順は §17)。
- 文字は 22px(本文)・24px(見出し)、入力欄とボタンは高さ 48px。**表示領域の高さが約 950px 以上(1920×1080 のブラウザなど)なら、スクロールなしで全項目が見える**。それより低い画面(1536×864・1366×768 など)では、左の 1〜4 だけが内側でスクロールし(項目が重なったり欠けたりはしない)、履歴は右で幅いっぱいに表示される(幅が足りないときは履歴だけ横スクロール)。画面幅 1500px 以下では左の列を少し細くする。

## 製番の指定実行

`app.main(config_path, products=[製番], output_root=出力先)` を呼ぶ。`products` を省略した従来の呼び出し(`app._cli`・定期実行)は変わらない。指定時は **ホストの製番一覧取得を省き**、その製番を既存の製番処理(`run_product`)に通す。対象判定・処理済み判定(出力先に既にあればスキップ)・失敗時の後始末は、製番処理の中で従来どおり行われる。

- 状態は `app.main` の結果をそのまま反映する: 完了 → **完了**、失敗 → **失敗**(理由つき)、処理済み・対象外 → **スキップ**(完了とは扱わない)、例外 → **失敗**。
- **推論 API の応答待ち(`api.request_timeout`、任意)**: `app.local.yaml` の `api.request_timeout`(秒)で、本番モードの `/predict` の応答待ちを設定できる。**省略すると従来どおり待ち続ける**(既定値なし。値は本番ログの実測に基づいて別途決める)。不正値(0・負・数でない値・float で表せない非常に大きな整数など)は、製番処理の開始前にエラーとなり、動作チェックの「設定の形式」も NG になる。超過した製番は、既存の失敗の扱い(失敗として記録・製番フォルダを削除・再試行なし)になる。詳細は `docs/inference_contract.md` §6。
- **推論 API の事前確認**: 本番モード(推論サーバーを自分で起動しない設定)では、`app.main` が重い処理(ホスト照会・設計データ・印刷・変換・画像作成)に入る前に、推論 API の `/health` を 1 度だけ確認する(通常処理・指定実行とも)。リダイレクトは追跡せず、最初の応答が HTTP 200 のときだけ「使える」とする。使えないとき(`server.yaml` が無い・読めない、接続拒否、タイムアウト、HTTP 200 以外(リダイレクトを含む))は、製番処理を始めず、履歴に「**失敗**」と理由(「推論 API を利用できないため、製番処理を開始しませんでした(…)」。接続先は含まない)を記録する。通常処理は「(全体)」、指定実行は指定した製番として失敗にする(完了・スキップ扱いにしない)。詳細は `docs/inference_contract.md` §2。統合モードと `run-scheduled --dry-run` の動作は変わらない。
- **二重起動の防止**: ロックファイルへの OS のファイルロック(排他)で、画面からの実行どうし、および画面とタスクスケジューラからの定期実行の間で排他する。実行中の開始は拒否される(画面では 409 の旨を表示、ボタンも無効)。ロックは持ち主のプロセスが終了(異常終了を含む)すれば OS が解放するため、古いロックは残らず、PID の使い回しも問題にならない。状態確認が一瞬ロックを取る間と重なっても、取得は短く再試行する。
- **`SystemExit`(`design_mod` の `sys.exit()` など)**: `app.main` の中で `SystemExit` が出ても、履歴は「**失敗**」で終わる(「実行中」のまま残らず、完了・スキップ扱いにもしない)。理由は固定の「処理が途中で終了しました(SystemExit)」で、終了コードやメッセージ(パス・秘密情報を含みうる)は記録しない。COM の終了処理とロックの解放は従来どおり行い、定期実行(`run-scheduled`)は終了コード 1 になる。製番フォルダ(部分出力)は、`app.main` 側の製番処理が既存の失敗と同じ後始末(出力ルート配下に限る削除)を行う(`docs/refactor_plan.md` §6)。`run-scheduled --dry-run` は `app.main` を呼ばないため影響しない。
- 画面を開き直したとき、終わりが書かれず「実行中」のまま残った履歴は「失敗(処理が途中で終了)」にする(プロセスが強制終了された場合など)。
- **COM の初期化・終了**: ホスト DB(`host_mod`)は COM(ADODB)を使う。メインスレッド以外では COM が未初期化で、`ADODB.Connection` の生成が `0x800401F0` で失敗し、`host_mod` は例外を握りつぶして「ホスト情報を取得できません」(スキップ)にしてしまう。そのため、**製番の実行(`ops-run` の worker スレッド。定期実行も同じ処理)** と **動作チェックのホスト照会(HTTP の要求スレッド)** は、呼ぶ前に同じスレッド内で `CoInitialize`、終わったら必ず `CoUninitialize` を呼ぶ(`ops/com.py`)。
  - 初期化に失敗したときは `app.main` を実行せず、履歴に「失敗(COM を初期化できないため実行しませんでした)」を残す(終了処理は呼ばない)。
  - 終了処理(`CoUninitialize`)が例外になっても、握って無視する。すでに決まった実行結果(完了・失敗・スキップと理由)は変えない。

## 定期実行(Windows タスクスケジューラ)

登録されるタスク(名前 `SekisanNaviData_Ops`)は、**N 日ごと**(画面の「間隔」。**2 = 1 日置き(既定)**、1 = 毎日)の指定時刻に、次を 1 回起動するだけ。

```
<python> ops_console.py run-scheduled [--config ...]
```

- `run-scheduled` は **製番も出力先も指定せず**、既存の通常処理(`app.main` の既定動作)を実行し、結果を履歴に「定期」として残す。製番検索・処理済み判定・実行間隔は変えない。出力先を 1. で保存していれば、その出力先で実行する。
- **検証用 `--dry-run`**: `ops_console.py run-scheduled --dry-run` は、タスクの起動経路を安全に確認するための入口。**ロックの取得 → COM の初期化 → ローカル設定(`ops.local.yaml`)の読込確認 → COM の終了 → ロック解放**だけを行い、**`app.main` は呼ばない**(ホスト DB・設計データ・共有・API・CAD には触れない)。履歴には種別「**定期(検証)**」・製番欄「(検証のみ)」で、開始と終了を記録する(理由は固定の文言。製番・出力先・ホスト名・設定値は記録しない)。
  - 状態: 完了(確認できた)/ 失敗(COM の初期化失敗・設定の読込失敗。理由に例外型だけ)/ スキップ(他が実行中のため二重起動の防止)。終了コードは、失敗のときだけ 1。
  - 画面の「3. 定期実行」が登録するタスクのコマンドは変わらない(`--dry-run` は付かない)。通常の `run-scheduled` の挙動も変わらない。検証したいときは、このオプション付きで手動起動するか、別名の検証用タスクに指定する。
- 登録・更新(`schtasks /Create … /F` と `/Change /ENABLE|/DISABLE`)と解除(`/Delete`)は、画面の明示操作でだけ実行する。表示のための照会(`/Query`)は読み取りだけ。
- **実行間隔(確定)**: 既定は **2 日 = 1 日置き**(`/SC DAILY /MO 2`)。元の運用は「1 日置きに出力可能な製番を検索し、未出力製番を処理する」で、毎日実行を既定にはしない。画面の「間隔」(1〜30 日)で変更できる(1 = 毎日)。製番の取得は「当月の出図済み製番 − 出力先にある処理済み製番」なので、間隔を変えても取りこぼしは起きず、処理が始まるまでの遅れとホスト照会の頻度が変わるだけ。
- **制約(初期版の仕様)**: タスクは、このコンピューターの**ログオン中のユーザーとして、ログオン中だけ**動く(`/RU` を付けない通常のタスク)。**ログオフ中は動かない**。この制約は画面(「3. 定期実行」の注記)にも表示する。**ログオフ中の実行を可能にする設定(パスワード保存の `/RU`・`/RP` など)は、初期版では追加しない。**
- **作業フォルダ**: タスクの既定の作業フォルダは System32 のため、`ops_console.py`(`serve`・`run-scheduled`)が起動直後にリポジトリのフォルダへ移る。設定の相対パスは、そこを基準に読む。
- **コマンドの引用**: `<python>`・`ops_console.py`・`--config` のパスはそれぞれ二重引用符で囲む(空白を含むフォルダでも動く)。`schtasks /TR` の上限(261 文字)を超えるときは、登録せずにエラーを表示する。
- テストでは `schtasks` の実行(`runner`)をモックし、`subprocess.run` が呼ばれたら失敗にする。**開発・テストでこの PC の実タスクは登録・変更・削除していない。**
